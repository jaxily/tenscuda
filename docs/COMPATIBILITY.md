# Model compatibility matrix

Generated by `python scripts/matrix.py MODEL` (one row per model, raw data in `results/matrix/`);
`python scripts/matrix.py --render` rebuilds this file. Do not edit the table by hand.

Setup: one P150a, single card, host with 8 GB RAM. TT runs use the streaming loader
(`tenscuda.loader`), bf16 weights, HiFi4 math with fp32 accumulation, a fixed-shape greedy loop,
batch 1, the chat prompt "Explain in two sentences why the sky is blue." and 32 new tokens.

- **parity vs CPU**: greedy tokens matching the CPU reference before the first difference. The
  reference is a plain greedy loop in fp32 if the model fits in host RAM, else bf16.
- **works (near-tie)**: the first difference is at a step where the CPU's top-2 logits are within
  0.25 of each other, which is about one bf16 rounding step at typical logit magnitudes.
  That's a precision effect, not an adapter bug.
- **warm tok/s**: decode speed of generate calls 2-4 (mean, min-max), after compilation.
- **first run s**: the first generate call, including TT-MLIR compilation.
- **peak host RSS**: process VmHWM after loading weights, and at the end.
- **CPU tok/s**: the CPU reference's decode speed on the same host (4 threads), for scale.
- **M4 pause Δ%**: only when the row was measured with `python scripts/matrix.py MODEL --pause-benchmark` (``TENSCUDA_DECODE_PAUSE_MODES=1`` vs default replay probe).

Notes:

- **CPU fallbacks: aten::_local_scalar_dense** comes from the teacher-forced parity forward
  (`use_cache=False`, the HF mask path reads a scalar). The fixed-shape generate loop that
  produces the tok/s numbers runs with no CPU fallbacks; `python -m tenscuda bench` reports none.
- **Near-ties:** Qwen2.5-0.5B diverges from CPU fp32 at step 16, where CPU's top-2 logits differ by
  0.21. Teacher-forced, TT picks the CPU token at all 32 positions. Qwen2.5-1.5B diverges at step 28,
  where CPU bf16 has an exact tie (margin 0.0) and TT has a 0.25 margin. That's a bf16 coin flip, not a bug.
- **Host RAM:** "anon" is peak RssAnon (sampled every 10 ms), the memory that has to fit in host RAM.
  VmHWM also counts the mmapped safetensors pages. torch-xla defers the host-to-device copy until
  the first execution, so the checkpoint is paged in then as reclaimable page cache.
- **Llama-3.2-1B / 3.2-3B / 3.1-8B** use ungated `unsloth/*` mirrors (same weights) where the
  Meta checkpoints are gated on this host.
- **Gemma-2-2B** uses `unsloth/gemma-2-2b-it` (`google/gemma-2-2b-it` is gated here). The loader
  rebuilds `Gemma2TextScaledWordEmbedding` buffers with `embed_scale = sqrt(hidden_size)`.
- **Phi-3.5-mini** greedy stream diverges at step 6 (CPU top-2 margin 0.25); teacher-forced is 31/32.
- **Llama-3.1-8B** CPU reference uses mmap'd bf16 on the 8 GB host (~0.53 GiB peak anon, slow).
  TT streaming load peak **anon** was 0.52 GiB; greedy and teacher-forced **32/32** vs CPU bf16.
- Device memory isn't shown. `xm.get_memory_info` is UNIMPLEMENTED in pjrt-plugin-tt
  1.5.0.dev20260831, and no other in-process route works yet (see docs/PERF.md).
